# Aqualung i770RのHISTORYリセット

Aqualung i770Rの累計情報（HISTORY）を、Bluetoothで0に戻した調査記録とPythonコードです。2026-10-02、バージョン応答が`AQUA770R 2A 0006`の実機1台で検証しました。総潜水本数（TOTAL DIVE）は206本から0本になりました。

リセットするのはHISTORYの16バイトです。総潜水本数に加え、累計時間・最大深度・最大潜水時間・深度合計も0に戻ります。**ダイブログは残るため、工場出荷時の状態には戻りません。**

実機で成功したのは調査用の試作コードです。公開版は試作コードを整理したもので、自動テストは通っていますが、公開版そのものの実機動作は未確認です。別機種や別バージョンでの書き込みも確認していません。

メーカー非公式の方法で、電源を切っても内容が残る不揮発メモリを書き換えます。校正値や内部状態と思われる領域に変化がないことは確認しました。一方、水中動作・減圧計算の正しさ・次の潜水番号は未検証です。この記録から潜水機器としての安全性は保証できません。

## 実機で確認した結果

| 項目 | 実機で確認した結果 |
|---|---|
| 対象 | i770R / `AQUA770R 2A 0006` |
| 通信 | Mac / Bluetooth LE / Python・Bleak |
| 変更範囲 | `0x0060–0x006F`、16バイト単位のページ6 |
| TOTAL DIVE | 206 → 0 |
| B2の応答 | `5A`（ACK） |
| 先頭256バイトの変化 | HISTORY内の9バイトのみ |
| 校正値と思われる領域 `0x0010–0x003F` | 変更前後で完全一致 |
| 内部状態と思われる領域 `0x3FE00` / `0x3FF00` | 各256バイトが変更前後で完全一致 |
| 切断・再接続後の読み取り | HISTORYの16バイトがすべて0 |
| 本体画面 | 所有者がHISTORYのリセットを確認 |

成功した送信では、`B2 + ページ番号 + データ16バイト + チェックサム`を1つのコマンドとして扱いました。チェックサムはデータ16バイトの合計です。ページ番号だけを先に送り、応答を待つ方法では拒否されました。送信するバイト列は[通信形式](docs/protocol.md)、変更前後の確認結果は[検証記録](docs/verification.md)に載せています。

## コードの位置づけ

試作コードは、他のローカルファイルを読み込む構成でした。公開版の[i770r_history.py](i770r_history.py)は、その依存を整理したコマンドラインツール（CLI）です。書き込み先をHISTORYのページ6に固定し、機器名・メモリ内の識別情報・バージョンを照合します。

書き込みはバックアップを保存してから行います。最初に書き戻すのは、現在と同じ値です。読み取った内容に変化がないことを確認し、成功した場合だけ0を書き込みます。その後、HISTORYと比較対象の領域を読み直します。

書き込みの受理応答（ACK）が来ない場合や、チェックサムが合わない場合は停止します。比較対象の領域に想定外の変化があった場合も停止し、自動再送や自動復元は行いません。公開版のテストではBluetooth機器の応答を模擬しています。実機で成功した記録と、この自動テストの結果は別のものです。

## 準備と読み取り

Python 3.11以上とBluetooth対応PCが必要です。環境の準備には[uv](https://docs.astral.sh/uv/)を使います。実機で成功した環境はApple SiliconのmacOSです。WindowsとLinuxでの実機動作は検証していません。

```sh
git clone https://github.com/Utopi-a/aqualung-i770r-history-reset.git
cd aqualung-i770r-history-reset
uv sync --locked
uv run i770r-history --help
```

コマンド内の`FQ123456`は例示用の名前です。自分のi770RがBluetoothで通知する機器名に置き換えてください。

1. 本体を水面モードで起こし、BluetoothをONにしてください。
2. USBクリップを外し、DiverLog+など他の接続を終了してください。
3. macOSがBluetoothへのアクセス許可を求めたら、使用するターミナルに許可してください。

まず、メモリを書き換えない`inspect`で現在のHISTORYを確認します。

```sh
uv run i770r-history inspect --name FQ123456
```

## HISTORYのリセット

次のコマンドでHISTORYを0にできます。`--backup`には、まだ存在しない保存先を指定してください。

```sh
uv run i770r-history reset-history \
  --name FQ123456 \
  --backup backups/before-history-reset \
  --confirm-reset-history
```

書き込み後の読み取りと比較まで成功すると、結果の`status`が`reset_verified`になります。ACKを受け取っただけでは成功と判定しません。全16バイトが既に0なら、書き込みを送らず`already_zero`を返します。

切断後は本体画面を確認し、もう一度`inspect`で読み取ってください。Bluetoothは画面のスリープ中に停止します。応答が止まった場合は自動再送されません。本体の状態と、保存された`failure.json`を確認してください。

## バックアップと復元

バックアップには機器の識別情報と、校正値・内部状態と思われる領域のデータが含まれます。GitHubにはアップロードしないでください。`backups/`とバイナリファイルは`.gitignore`で除外しています。POSIX環境では保存先の権限を0700、ファイルの権限を0600にして作成します。保存するのは比較に使う領域だけで、全メモリではありません。

HISTORYだけを元に戻す場合は、同じ機器から取得したバックアップを指定します。

```sh
uv run i770r-history restore-history \
  --name FQ123456 \
  --backup backups/before-history-reset \
  --confirm-restore-history
```

復元するのはHISTORYの16バイトだけです。バックアップのSHA-256でファイルの内容を確認し、機器の識別情報も照合します。復元条件は、現在のHISTORYが全て0か、バックアップと同じ値であることです。比較対象の他の領域も、バックアップと一致している必要があります。

新しい潜水などで比較対象の状態が変わっていれば、復元を拒否します。校正値や内部状態と思われる領域を書き戻す機能はありません。

ACKが届かない場合、書き込みが反映されたかどうかは不明です。同じ復元を自動で繰り返すことはありません。保存先に`restore-attempt.json`が既にある場合も、新たな復元書き込みを送りません。

## ログと表示番号

HISTORYとダイブログは別の領域に保存されています。HISTORYを0にしても、古いダイブログは残ります。

調査ではログ本文を`FF`で埋める操作も試しました。しかし、ログの位置を管理する索引が残り、本体のログ選択欄も消えませんでした。索引の変更は応答が得られず、ログ消去は達成していません。

その後、本文の全606ページを元のバックアップから復元し、完全一致を確認しました。公開ツールには、ログ本文を`FF`で埋める機能を含めていません。

`8 → 7 → … → 1 → 99 → 98 …`という表示番号だけでは、記録の順序が乱れたとは判断できません。復元した索引が参照する99件は、新しい記録から順に並び、重複なく元の記録と対応しました。ただし、本体画面の日付順と番号の表示規則は未確認です。詳しくは[ログ番号と順序](docs/log-order.md)を参照してください。

## テスト

自動テストは実機に接続せず、Bluetoothの送受信部分（GATT）の応答を模擬して実行します。

```sh
uv run python -m unittest discover -s tests -v
uv run python -m compileall -q i770r_history.py tests
```

テスト対象は、送信形式とチェックサム、同じ値の書き戻し、HISTORYだけの変更、バックアップと復元です。機器やバージョンの不一致、拒否応答（NAK）、ACKの欠落、読み取り結果の不一致で停止することも確認します。模擬応答によるテストだけでは、実機動作や水中動作は確認できません。
