# 実機と公開コードの検証記録

HISTORYのリセットは、調査用の試作コードで実機確認しました。公開コードではBluetooth機器の応答を模擬した自動テストを行っています。公開コードそのものの実機動作は未確認です。

## 実機で成功した試作版

2026-10-02、バージョン応答が`AQUA770R 2A 0006`のi770Rで検証しました。使用した環境はApple SiliconのmacOSで、接続にはBluetooth LEを使いました。機器名・シリアル番号・個人情報・メモリの生データ・APK・バグレポートは公開していません。

変更前に低位メモリを読み取り、HISTORYの保存位置と本体表示の対応を確認しました。バックアップと現在値を照合した後、HISTORYと同じ値を`B2`で書き戻しました。受理応答（ACK）は`5A`で、先頭256バイトに変化はありませんでした。

次に、内部状態と思われる2ブロックを保存しました。HISTORYの16バイトに0を書き込むと、ACK `5A`が返りました。同じ接続で読み直した結果、TOTAL DIVEは0、HISTORYの全16バイトも0でした。先頭256バイトで変わったのは、HISTORY内の9バイトだけです。

校正値と思われる48バイトと、内部状態と思われる2ブロック各256バイトは、変更前後で完全一致しました。切断・再接続後にも、HISTORYの全16バイトが0であることを確認しています。所有者も本体画面でリセットを確認しました。

個人情報や機器固有データを除いた結果を[evidence/hardware-reset-2026-10-02.json](../evidence/hardware-reset-2026-10-02.json)に保存しています。このJSONは確認結果の記録です。元のメモリを再現できるデータは含まれていません。

## ログ消去の試行

HISTORYのリセットとは別に、ログ本文606ページを`FF`で埋める操作を試しました。全ページでACKが返り、読み直しも成功しました。しかし、ログの位置を管理する索引は残り、本体のログ選択欄も消えませんでした。

この時点で「8→7→…→1→99→98…」という表示が報告されました。番号の並びだけでは、記録の順序が乱れたかどうかは判断できません。確認できたのは、本文を`FF`で埋めてもログが0件にならなかったことです。

そのため、全606ページを消去前のバックアップから復元しました。606ページ全てでACKを受け取り、読み直した内容もバックアップと完全一致しました。HISTORYは0のままです。校正値と思われる領域・MY INFO・内部状態と思われる領域も維持しました。その後はログ本文の消去を行っていません。

索引を含む管理ページ4の変更は成功しませんでした。通常の接続に加え、公式アプリの復元用開始手順`82`や、フレーム長・Bluetoothの送信方式（ATT方式）を変えても応答は得られませんでした。

応答がない理由は不明です。書き込み保護やEEPROMの故障が原因だとは断定していません。最後に機器全体を再確認しようとしましたが、再接続できず、電波も検出できなかったため完了していません。

## 公開コードの自動テスト

公開用のコマンドラインツール（CLI）は、成功した試作コードを整理したものです。公開コードを検証するために、実機のHISTORYを再度変更することはしていません。

不揮発メモリを書き換えるため、誤った操作の影響は大きいと判断しました。そこで、書き込み前のバックアップ、変更範囲の固定、異常時の停止をテストの確認項目にしています。

模擬するのはBluetoothの送受信部分（GATT）だけです。送信データの組み立て、受信データの解析、チェックサム、ファイルへの保存、前後の照合には公開コードの実装を使います。

| 確認する動作 | テスト方法 |
|---|---|
| B2コマンド全体を20/8バイトのフレームで送る | 実機で確認した形式のバイト列と照合 |
| 機器やバージョンが一致しない場合は停止 | 模擬した機器との送受信テスト |
| inspectではメモリを書き換えない | 模擬した機器との送受信テスト |
| バックアップを上書きしない | 実ファイルシステムでのテスト |
| 同じ値の書き戻しと読み直しに成功してから0を書く | 模擬した機器との送受信テスト |
| HISTORY以外の比較対象領域と内部状態と思われる領域を維持 | 比較対象の全バイトを前後で照合 |
| NAK・ACK欠落・チェックサム不一致で停止 | 模擬応答で停止し、自動再送が0回であることを確認 |
| ACKだけでは成功と判定しない | ACKを返しても書き込みを反映しない模擬機器で確認 |
| HISTORYだけを復元し、新しい状態を上書きしない | 変更されたバックアップ・別機器・新しいHISTORYの拒否を確認 |
| 書き込みコマンドには明示的なフラグが必要 | CLI引数テスト |

別のレビュアーによる独立した確認、公開CLIの実機テスト、水中テストは行っていません。別OSや別ファームウェアでの実機動作も未検証です。自動テストだけでは、これらを確認したことにはなりません。

## HISTORYの復元と応答がない場合の扱い

保存したバックアップから、HISTORYの16バイトだけを戻すコマンドを用意しています。校正値や内部状態と思われる領域を含む全メモリの復元は行いません。新しい潜水などで比較対象の状態が変わっていれば、復元を拒否します。

書き込みへの応答がない場合、実際に保存されたかどうかは不明です。切断して状態を確認し、同じ書き込みを自動では繰り返しません。エラーやバイト比較の不一致を無視して、成功と判定する処理もありません。
